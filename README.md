# The Beach House on Suttons — suttonsbeach.net

Static marketing site and guest guide for a privately owned 3-bedroom holiday
apartment at 43 Marine Parade, Redcliffe, Queensland.

**Live site:** https://suttonsbeach.net/
**Repository:** https://github.com/Pakton-Paul/BeachHouse
**Owners:** PD & KJ Thompson

---

## Purpose and context

The site exists to showcase the property to potential guests. It is **not** a
booking engine and deliberately does not take bookings or payments directly.

The property is let short-term through **Airbnb** and swapped through
**HomeExchange**. It is not intended to be let 52 weeks a year — the owners
keep flexibility for family and friends, and price it at the top of the market
to keep wear and tear down and presentation high.

Because of this, every call to action on the public page points at one of the
two platforms:

| Platform | Listing |
| --- | --- |
| Airbnb | https://www.airbnb.com.au/rooms/46904216 |
| HomeExchange | https://www.homeexchange.com/holiday-home/2906465 |

The contact form is only for people who want an **introduction to
HomeExchange** (it is a members-only platform) or who have a general question.

## How it is built and served

There is **no build step, no framework and no package manager**. It is hand-written
HTML, CSS and vanilla JavaScript.

Hosting is **GitHub Pages**, serving the `main` branch from the repository root,
with the custom domain `suttonsbeach.net` set via the `CNAME` file.

**Deploying = pushing to `main`.** A push typically goes live within a minute or
two. There is no staging environment.

External dependencies are all loaded from CDNs — there is nothing to install:

- **Font Awesome 6.2.0** (icons) via cdnjs
- **Google Fonts** — Roboto for headings, Arial for body
- **Google Maps** embed iframe on `index.html`
- **Web3Forms** for form submissions

### Web3Forms

All three forms (enquiry on `index.html`; testimonial and issue report on
`guests.html`) POST to `https://api.web3forms.com/submit` with a hidden
`access_key`. Submissions are emailed to the address registered with that key at
web3forms.com. The key is public by design — it only permits sending to the
registered address. If the destination email needs to change, that is done in the
Web3Forms account, not in this repo.

## Working on the site locally

Clone, then serve the folder over HTTP. Opening `index.html` directly with
`file://` mostly works but can behave oddly with the manifest and absolute paths.

```bash
git clone https://github.com/Pakton-Paul/BeachHouse.git
cd BeachHouse

# Python 3
python -m http.server 8000
```

Then visit:

- http://localhost:8000/ — public page
- http://localhost:8000/guests.html — guest guide
- http://localhost:8000/exit-checklist.html — departure checklist
- http://localhost:8000/building-rules.html — building rules

### Conventions worth knowing

- **Colours** live as CSS variables in `:root` at the top of `style.css`. Change
  them there, not inline.
- **Page-specific CSS** goes in a `<style>` block in that page's `<head>`.
  Anything shared belongs in `style.css`.
- **Guest guide pages must keep** the `noindex, nofollow` robots meta tag.
- **`index.html` must keep** the phrase *"Gunge Heifers"* in the footer. It is a
  deliberate nonsense phrase used to check whether Google has indexed the page —
  searching for it should return the site.
- **Images** are PNG in `images/`, referenced with lowercase underscore names.
  Some `<img>` tags carry leftover `?text=...` query strings; these are harmless
  and can be stripped when touching that markup.
- **Line endings** are normalised by `.gitattributes` to LF in the repository.
  Without it, editing on Windows produces diffs where every line of every file
  appears changed.
- **`.gitignore` must be saved as UTF-8.** It was previously UTF-16, which git
  silently fails to parse, causing ignored folders to be committed anyway.

## The exit checklist

`exit-checklist.html` is an interactive checklist. Each item is a `<li>` with a
unique `data-id`. Clicking (or pressing Space/Enter when focused) toggles a
`done` class; the state is written to `localStorage` under the key
`bhos_exit_checklist_v1`, so a guest's progress survives a page reload. A sticky
progress bar and a Reset button sit at the top.

**When adding a new checklist item, give it a `data-id` that has never been used
before.** Reusing an id means returning guests see the new item already ticked.
Changing the storage key resets everyone's progress, which is the clean way to
handle a large rewrite of the list.

The pattern is borrowed from a sister site:
https://paktonpaul.github.io/RR-Rd-Website/orientation-checklist.html
